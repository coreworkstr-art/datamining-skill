# Privacy and security

## Guarantees

1. **No network access.** The runtime package imports no networking modules and has
   no third-party dependencies. Data processing never leaves the process.
2. **No uncontrolled data copies.** Input files are opened with mode `rb` only and are
   never modified. The chunking engine writes nothing. Mining writes only what is
   deliberate and local: the result file you name; per-chunk scratch files
   (`chunk_{id}.tmp`, deleted as each chunk is merged); the chunk-state database and its
   lock file (metadata, plus, for a unique job, one 16-byte hash per distinct record, deleted
   when the job finishes); and, for a compressed or UTF-16 source, a temporary UTF-8 copy
   (deleted when the job finishes). `profile` of a compressed file keeps a 4 MiB decompressed
   sample for the duration of the call. All of these are confined to `.scratch/` or `data/`;
   the code never calls `tempfile` or uses the system temporary directory.
   Files are created `0600` and directories `0700` on POSIX; on Windows a protected
   owner-only ACL is applied (see below). Regression tests fail if the profiler touches
   `tempfile` or modifies the source, and if a scratch or state path escapes its allowed
   directory (including via `..` or symlinks). The output may not be the source file.
3. **No content in logs or errors.** Log events and exception messages carry file
   names, sizes, timings, memory figures and format labels only. A test asserts
   that a unique marker inside the data never appears in log output. Directory
   paths are deliberately omitted as well.
4. **Safe parsing.** Input is tokenised, never executed:
   - JSON via `json.loads` (data structures only); parse failures including
     `RecursionError` from pathologically nested input are caught and counted as
     invalid lines.
   - CSV via the `csv` module (tokenising only).
   - Logs via anchored regular expressions applied to at most the first 2048
     characters of a line, which bounds worst-case matching time.
   - No `eval`, `exec`, `pickle`, `marshal`, `yaml.load` or dynamic imports.
5. **Denial-of-service resistance.** All buffers are capped (see
   [architecture.md](architecture.md#memory-model)). Oversized lines are searched in bounded
   windows (profiling truncates them and skips the remainder in constant space); NUL-bearing
   content and archive formats that cannot be converted are rejected before parsing. A
   compressed source is expanded as a stream, stopped at an expansion limit and when free disk
   space runs low, and never leaves a partial copy. Undecodable bytes are replaced rather than
   raising.
6. **Strict configuration.** TOML configuration is loaded from a local file only;
   unknown keys, wrong types and out-of-range values are rejected.

## MCP threat model

An MCP client (an AI assistant) calls the server's tools with arguments that were generated by
a language model, possibly influenced by untrusted text it has read (prompt injection). The
server therefore treats every argument as untrusted input from a *less* trusted principal than
the person who started it.

| Threat | Mitigation |
| --- | --- |
| Reading files outside the intended area (`../`, absolute paths, symlinks) | `WorkspacePolicy` resolves each path (following `..` and symlinks) and requires it to lie strictly inside an `--allow-dir` directory. Relative paths resolve against the workspace. Error text names allowed directories but never echoes resolved paths or contents. |
| UNC and device paths (`\\host\share`, `\\?\`, `\\.\`) | Rejected from the path *text*, before any filesystem call. Resolving a UNC path makes Windows open an SMB connection (and offer the user's NTLM credentials), so a containment check performed after `resolve()` would already have contacted a remote machine. |
| Names Windows silently rewrites: alternate data streams (`file.csv:hidden`, `::$DATA`), reserved devices (`NUL`, `CON.txt`, `COM1`), trailing dots or spaces | Rejected on Windows from the path text. |
| Control characters, `%00`, `~`, `$HOME` | Control characters are rejected everywhere (log and terminal forgery). `%00`, `%2e%2e`, `~` and environment references are never decoded or expanded: they are ordinary file-name characters. |
| Planted `.scratch` symlink or junction | `run_layout` refuses a `.scratch` that resolves outside the workspace; otherwise state and chunk files, which contain mined data, could be redirected anywhere. |
| Overwriting arbitrary files through `output_path` | Output must end in `.csv`, `.jsonl` or `.ndjson` and be inside an allowed directory; an existing result is never replaced unless `overwrite` is true; the output may not be the source file. |
| Denial of service through a model-written regular expression | `pattern`/`fields` are not even declared unless the operator starts the server with `--allow-custom-patterns`, which prints a warning to stderr at startup. Even then, patterns that repeat a repeating group without an upper bound (`(a+)+`, `(a{1,64})+`) are rejected. This filter is defence in depth, not a guarantee: `re` has no time limit and overlapping alternations such as `(a\|aa)+` are not detected. |
| A decompression bomb (`bomb.csv.gz`) | A compressed source is expanded as a stream into a private file in `.scratch/`, never into memory. The expansion is capped (`--max-expanded-gib`, default 64 GiB) and stops when less than 1 GiB of disk is free; the partial copy is deleted. A zip archive must hold exactly one unencrypted file. |
| Reading a result file through `preview_result` | Only `.csv`, `.jsonl` and `.ndjson` files inside the allowed directories, and at most 256 KiB are read, whatever the file's size. |
| Exhausting the machine with background jobs | At most four run at once; an identical job cannot be started twice; they use the same bounded-memory pipeline and the same per-job lock as a foreground run. |
| Oversized or malformed messages | Messages are read in bounded pieces (1 MiB limit) and rejected without losing synchronisation; JSON that is too deep is rejected as a parse error. |
| Over-broad workspace | With no `--allow-dir` and no `DATAMINING_SKILL_ALLOWED_DIRS`, the server uses its working directory and refuses to start if that is the filesystem root. |
| Corrupting the protocol channel | stdout carries only JSON-RPC messages; `print` is redirected to stderr while serving. |
| Leaking information in results | Tool results contain names, counts, workspace-relative paths and (for `profile_dataset`) column names or JSON keys. Mined records go only to the output file; they are never returned to the client or logged. |

Residual risks, stated plainly:

- The result file and `profile_dataset` output reflect the data the assistant was allowed to
  read. Column names and JSON keys come from the file and are shown to the model; a hostile
  file can contain text intended to manipulate it.
- Path checks happen at call time. A local process that can already write to the allowed
  directories could swap a file for a symlink between the check and the open.
- `--allow-custom-patterns` re-introduces the regular-expression denial-of-service risk.
- Treat the allowed directories as readable and writable by whatever drives the client.
- A unique job stores a hash of every distinct record while it runs. For low-entropy values such as
  e-mail addresses a hash can be reversed by guessing, so treat the state database as sensitive as
  the result file (it is owner-only and removed when the job finishes).
- A converted copy of a compressed or UTF-16 source holds the whole text while a job is unfinished.
  If a run is abandoned, `datamining-skill clean --all` removes it.

## Security controls and how they are verified

`tests/test_security.py` turns each control below into a regression test. Disabling a
control (ACL restriction, link check, path-text vetting, pattern vetting, terminal-escape
sanitising) makes the matching tests fail; this was checked by switching each one off.

### Network isolation

- No module that can reach the network, spawn a program or execute data is imported: a static
  scan of every runtime module checks imports, calls and hard-coded URLs or addresses, and a
  fresh interpreter that runs a full profile, mine and MCP session is checked to have loaded none
  of them (`socket`, `ssl`, `http`, `urllib`, `subprocess`, `asyncio`, ...).
- A runtime guard replaces `socket.socket` and every name-resolution function with a failing stub
  while a complete session runs, so an outbound call would fail the test.
- The only native libraries the runtime loads are `kernel32` and `advapi32` (memory figures and
  Windows ACLs). The only log handler is a stderr stream handler.
- There is no telemetry, update check or analytics of any kind.

### SQL safety

- `sqlite3` is imported by exactly one module. Every executed statement is a module-level string
  constant; values are always bound with `?`. A static test fails if SQL text is ever built with an
  f-string, `%`, `+` or `.format`. Database file names never reach SQL.
- After 14 rounds of killing a worker with `kill -9` / `TerminateProcess` at random moments,
  `PRAGMA integrity_check` is `ok` every time and the status table and the commit ledger agree
  exactly (every COMPLETED chunk has its ledger row), so no crash can leave them inconsistent.

### File permissions (least privilege)

| Object | POSIX | Windows |
| --- | --- | --- |
| State database | created `0600` | protected ACL: current user, SYSTEM, Administrators |
| `-wal` / `-shm` side files | take the database file's mode | inherit the private ACL of their directory |
| Scratch and state directories (and output directories created for the user) | created `0700` | protected, inheritable ACL as above |
| Chunk scratch files | created `0600` | inherit the private directory ACL |
| Result file | created `0600` | protected ACL as above |

Modes are passed explicitly, so they do not depend on the umask (a test runs with `umask 0`).
Only objects this package creates are changed; an existing directory keeps its permissions.

Windows has no mode bits: new files inherit their parent's ACL, and on a volume outside the user
profile that commonly grants read access to **every local user**. (On the development machine,
`D:\` granted `BUILTIN\Users` read and `Authenticated Users` modify.) The package therefore sets a
protected ACL itself, using the Windows security API through `ctypes`. Tests read the resulting
ACL back from the operating system and assert that no broad trustee (Everyone, Users,
Authenticated Users, Interactive, Network, ...) is present. Applying an ACL is best-effort: on a
file system without ACLs (FAT) the call fails quietly and the object keeps whatever it inherited.

### Terminal safety

File names appear in error messages. A name containing an ANSI escape sequence or a bidirectional
override could rewrite the user's terminal, so messages escape every non-printable character
(`\x1b`, `\u202e`, ...). JSON output and structured logs are already escaped by the JSON encoder.

### Residual risks

- **Time-of-check / time-of-use.** Paths are validated, then opened. A local process that can already
  write inside the allowed directories could swap a file for a link in between.
- **Hard links** cannot be told apart from ordinary files by path, so a hard link inside the
  workspace to a file outside it is not detected.
- **Administrators and SYSTEM** retain access on Windows (as they do to any user profile), and root
  can read anything on POSIX.
- **Regular expressions.** See the MCP threat model; custom patterns remain an opt-in risk.
- **Durability.** Files are `fsync`ed; on macOS an `fsync` does not force data out of the drive's own
  cache (`F_FULLFSYNC` would), so a power cut can lose the most recent checkpoints (never corrupt data).
- **Case-insensitive file systems.** Containment comparison is case-sensitive on POSIX; on macOS this
  can only cause a legitimate path to be refused, never an escape to be accepted.

## Operator responsibilities

- Structured logs include file names. If file names are sensitive, do not enable
  logging or route stderr accordingly.
- Test data and the dummy-data generator write inside the project directory
  (`.scratch/`, `data/`), both git-ignored. Delete generated datasets when finished.
- Finished jobs leave a small state database under `<workspace>/.scratch/`. Remove them with
  `datamining-skill clean`; it never touches a result file or a job that is running.
- The profiler reports **structure only** (column names, JSON keys, field types).
  Column names can themselves be sensitive; treat output accordingly.
- The **mining result file contains the extracted data itself** (for example e-mail
  addresses), unencrypted. Choose its location and permissions accordingly, and delete
  it when no longer needed. Do not rely on the toolkit to anonymise it.
- If a mining process is killed, the result file may end in uncommitted bytes until the
  run is resumed; treat the file as final only after a run has completed.
- Opening a mined CSV in a spreadsheet can execute formulas hidden in the data. Enable
  `csv_formula_guard` (or use JSONL) when results will be opened in a spreadsheet.

## Reporting vulnerabilities

Please report suspected vulnerabilities privately through the repository's security
advisory feature rather than a public issue.
